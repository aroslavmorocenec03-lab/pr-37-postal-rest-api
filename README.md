# Практична робота №37

## Розробка простого RESTful API

**Тема документа:** створення простого ендпойнта для роботи з даними.

**Мета:** створити поштовий API, який повертає JSON і підтримує додавання, читання, редагування та видалення відправлень.

Розроблено **PostService** на ASP.NET Core Minimal API. Додано модель `Posting`, перелік `DeliveryType`, спільний `List<Posting>` у `Program.cs`, три початкові записи та всі п’ять маршрутів CRUD. Кореневе повідомлення з ПР-36 збережено.

## Запуск

Потрібен **.NET SDK 10**. Завантажте репозиторій через **Code → Download ZIP**, розпакуйте та відкрийте термінал у кореневій папці.

```powershell
dotnet build PostService/PostService.csproj
dotnet run --project PostService
```

Сервер працює на **`http://localhost:5050`**. Поки він запущений, у браузері або HTTP-клієнті можна отримати список за адресою `http://localhost:5050/postings`. Для зупинення натисніть **Ctrl+C** у терміналі сервера.

Усі запити для ручної перевірки: **[requests/postings.rest](requests/postings.rest)**. На новому запуску POST створює запис з `id = 4`; якщо дані вже змінювалися, підставте фактичний Id у змінну `@postingId`.

## Модель

Файл **[PostService/Models/Posting.cs](PostService/Models/Posting.cs)** містить клас `Posting` і самостійний перелік:

```csharp
public enum DeliveryType
{
    Department,
    Courier,
    ExpressCourier
}
```

| Властивість | Тип | Призначення |
| --- | --- | --- |
| `Id` | `int` | Унікальний ідентифікатор |
| `From`, `To` | `string` | Відправник та отримувач |
| `Content` | `string` | Вміст посилки |
| `DeliveryType` | `DeliveryType` | 0 — відділення, 1 — кур’єр, 2 — експрес-кур’єр |
| `Weight` | `float` | Вага |
| `Width`, `Height`, `Depth` | `float` | Розміри |
| `Value` | `float` | Оголошена цінність |
| `Price` | `float` | Вартість пересилання |
| `CreatedAt` | `DateTime` | Час створення |

Типи `float` відповідають моделі з завдання. ASP.NET Core повертає JSON із назвами властивостей у camelCase; значення переліку серіалізуються числами. `CreatedAt` сервер задає через `DateTime.UtcNow`.

## Маршрути та статуси

Основний код: **[PostService/Program.cs](PostService/Program.cs)**.

| Метод і шлях | Дія | Успіх | Запис відсутній |
| --- | --- | --- | --- |
| `GET /` | Повідомлення «Це API поштового клієнта.» | 200, текст | — |
| `GET /postings` | Усі відправлення | 200, JSON-масив | Порожній масив `[]` |
| `GET /postings/{id}` | Одне відправлення | 200, JSON-об’єкт | 404 |
| `POST /postings` | Створення | 201, JSON-об’єкт і заголовок `Location` | — |
| `PUT /postings/{id}` | Оновлення | 200, оновлений JSON-об’єкт | 404 |
| `DELETE /postings/{id}` | Видалення | 204 без тіла | 404 |

Приклад тіла POST:

```json
{
  "from": "Grace",
  "to": "Henry",
  "content": "Documents",
  "deliveryType": 0,
  "weight": 1.5,
  "width": 20,
  "height": 10,
  "depth": 5,
  "value": 200,
  "price": 30
}
```

`Id` і `CreatedAt` при створенні визначає сервер. PUT приймає повний набір редагованих полів, використовує Id зі шляху та зберігає початковий `CreatedAt`. У списку замінюється лише відповідний запис, а інші відправлення лишаються без змін.

Список та лічильник Id захищені `lock`, оскільки HTTP-запити можуть надходити одночасно. Для нового Id використано окремий зростаючий лічильник: він працює і після очищення списку та не перевикористовує щойно видалені Id в межах поточного процесу. GET списку повертає знімок через `ToArray()`.

Дані зберігаються в оперативній пам’яті. Після перезапуску знову створюються три початкові записи з Id 1, 2, 3; внесені під час попереднього запуску зміни не зберігаються.

## Перевірка роботи

Збірка виконана без помилок і попереджень. Реальними HTTP-запитами підтверджено **13/13 перевірок**:

- кореневе повідомлення, початкові три записи, усі поля та JSON;
- POST зі статусом 201, `Location`, серверним Id і часом UTC;
- GET створеного запису;
- PUT усіх десяти редагованих полів зі збереженням Id та `CreatedAt`;
- збереження змін та незмінність іншого запису;
- DELETE зі статусом 204 і порожнім тілом;
- 404 при GET, PUT та DELETE відсутнього запису;
- читання порожнього списку;
- створення записів після видалення всіх попередніх та унікальність нових Id.

Фактичні запити, статуси й тіла відповідей: **[reports/http-checks.txt](reports/http-checks.txt)**.

Щоб повторити перевірку, запустіть новий екземпляр сервера з початковими даними, а в другому терміналі **PowerShell 7** виконайте:

```powershell
./scripts/Verify-Api.ps1
```

Сценарій перевіряє операції зміни даних, включно з очищенням навчального списку. Після нього в пам’яті лишаються два створені перевіркою записи. Новий запуск сервера відновить початковий набір.

## Короткий висновок

Створено повний CRUD-цикл для ресурсу поштових відправлень. Прив’язування JSON до моделі спрощує отримання вхідних даних, маршрути з `{id:int}` дозволяють звертатися до окремого ресурсу, а статуси 201, 200, 204 і 404 пояснюють результат операції. Зберігання в `List<Posting>` дало змогу перевірити API без налаштування бази даних.

## Відповіді на контрольні запитання

1. **Що таке ендпойнт у REST API?** Це точка доступу до операції над ресурсом, яку визначають HTTP-метод і шлях. Наприклад, `GET /postings/1` читає відправлення 1, а `DELETE /postings/1` його видаляє.
2. **Для чого GET?** Для отримання представлення ресурсу без зміни його стану. У роботі ним отримують повний список або один запис.
3. **Які дані може повертати API?** Об’єкти й масиви у JSON, звичайний текст, XML, двійкові файли та інші формати відповідно до `Content-Type`. Деякі відповіді, як DELETE 204, не мають тіла.
4. **Що означає JSON?** JavaScript Object Notation — текстовий формат структурованих даних. Він підтримує об’єкти, масиви, рядки, числа, логічні значення та `null` і використовується багатьма мовами.
5. **Як дані зберігаються в пам’яті?** У цьому застосунку список `List<Posting>` оголошено в `Program.cs`; його захоплюють обробники маршрутів і використовують протягом життя процесу. Після завершення процесу цей стан втрачається.
6. **Яка роль маршруту в URL?** Шлях указує на ресурс або колекцію, а параметр `{id:int}` визначає конкретний запис. Разом із методом HTTP він дозволяє маршрутизатору обрати потрібний обробник.
7. **Як визначити ендпойнт списку?** Наприклад, `app.MapGet("/postings", () => Results.Ok(postings.ToArray()));`. У проєкті отримання знімка додатково захищено спільним блокуванням.
8. **Які компоненти потрібні для простого API?** Вебпроєкт ASP.NET Core, модель даних, сховище, маршрути з обробниками та HTTP-сервер. Для перевірки потрібен клієнт, наприклад браузер, PowerShell або редактор із підтримкою `.rest`.
9. **Чому важливий структурований формат?** Клієнт може розпізнати окремі поля, списки, числові значення й типи, а не аналізувати довільний текст. Це полегшує автоматичну обробку та обмін між різними мовами.
10. **Як перевірити ендпойнт?** Надіслати запит із правильним методом, адресою й тілом, перевірити статус, заголовки, формат і вміст відповіді. Для операцій зміни додатково виконати GET і переконатися, що новий стан збережено. Важливо перевіряти і відсутній запис.
